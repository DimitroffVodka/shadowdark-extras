# Hexplorer → Edit Hex → Features: current implementation

**Scope.** Static audit of the current Shadowdark Extras worktree, centered on
`scripts/hex/HexTooltipSD.mjs`, its Edit Hex template, the record seam, import
and builder consumers, tests, and the project's Hexroll/Hexplorer prior-art
references. This report describes current behavior; it does not propose or
implement fixes.

## Executive findings

- The Edit Hex row exposes **12** literal values: `dungeon`, `settlement`,
  `landmark`, `ruins`, `temple`, `fort`, `cave`, `road`, `hazard`, `resource`,
  `other`, and `journal`. The visible label is generated by capitalizing the
  value, so the labels are `Dungeon`, `Settlement`, `Landmark`, `Ruins`,
  `Temple`, `Fort`, `Cave`, `Road`, `Hazard`, `Resource`, `Other`, and
  `Journal`. [`scripts/hex/HexTooltipSD.mjs:51-54`](../../scripts/hex/HexTooltipSD.mjs#L51-L54)
- Eleven values are descriptive pills only. `journal` is the only user-selectable
  value with special Edit Hex behavior: it swaps the free-text label for a
  Journal and optional Page selector, and it participates in the right-click
  Journal-opening path. [`scripts/hex/HexTooltipSD.mjs:153-161`](../../scripts/hex/HexTooltipSD.mjs#L153-L161)
  [`scripts/hex/HexTooltipSD.mjs:1687-1764`](../../scripts/hex/HexTooltipSD.mjs#L1687-L1764)
- `scene` is a real internal feature type emitted by **Generate Dungeon Map**,
  but it is absent from the Edit Hex allowlist. An existing scene feature is
  therefore not representable by a matching option in the editor; saving that
  row reads the selected UI value and can turn it into the first listed value
  (`dungeon`) while leaving its old `sceneId` attached. This is a source-level
  data-integrity risk, not a runtime reproduction in this audit.
  [`scripts/hex/HexTooltipSD.mjs:51-54`](../../scripts/hex/HexTooltipSD.mjs#L51-L54)
  [`scripts/hex/HexTooltipSD.mjs:1287-1294`](../../scripts/hex/HexTooltipSD.mjs#L1287-L1294)
  [`scripts/hex/HexTooltipSD.mjs:1697-1700`](../../scripts/hex/HexTooltipSD.mjs#L1697-L1700)
  [`scripts/hex/HexTooltipSD.mjs:1802-1822`](../../scripts/hex/HexTooltipSD.mjs#L1802-L1822)
- The feature schema is structurally loose at the storage boundary. The editor
  writes `id`, `type`, `name` or Journal references, and `discovered`; the
  persistence function writes the whole record without validating feature
  entries. The public hexcrawl builder validates array/entry shape but accepts
  any string as `type`, so it is not the same as the UI taxonomy.
  [`scripts/hex/HexTooltipSD.mjs:1768-1825`](../../scripts/hex/HexTooltipSD.mjs#L1768-L1825)
  [`scripts/hex/HexTooltipSD.mjs:75-90`](../../scripts/hex/HexTooltipSD.mjs#L75-L90)
  [`scripts/hex/HexcrawlBuilderSD.mjs:268-303`](../../scripts/hex/HexcrawlBuilderSD.mjs#L268-L303)
- Hover-card visibility and feature discovery are separate gates. Players need
  `showToPlayers` to receive the card, then only `discovered` features appear
  in that card. The right-click path does **not** check `showToPlayers`; a
  discovered Journal feature can therefore be offered in the player context
  menu even when the basic hover card is hidden. [`scripts/hex/HexTooltipSD.mjs:526-545`](../../scripts/hex/HexTooltipSD.mjs#L526-L545)
  [`scripts/hex/HexTooltipSD.mjs:596-614`](../../scripts/hex/HexTooltipSD.mjs#L596-L614)
- Existing tests cover imported POI mapping, discovery defaults, escaping in the
  Hexer adapter, generic builder validation, and settlement tile rendering.
  They do not directly exercise the Edit Hex template/row handlers, feature
  collection, the `scene`-type round trip, or player/GM tooltip and context-menu
  rendering. The two relevant suites run directly in this audit passed **27/27**
  tests; this was not a claim that the full repository suite was run.

## 2. Stored shape and semantics

The current code does not declare a standalone feature schema. The effective
shape assembled by the editor is:

```text
id:          string              # generated for new rows; preserved for matches
type:        string              # one of the UI values when newly collected
name:        string              # free-text types; forced to "" for Journal
journalId:   string, optional    # Journal type and generated Journal links
pageId:      string, optional    # optional Journal page
sceneId:     string, optional    # internal scene shortcut, generated only
maphub:      object, optional    # generated settlement viewer metadata
discovered: boolean             # per-feature discovery/visibility flag
```

The editor's collector starts each row by spreading the matching existing
object, then overwrites `id`, `type`, and `discovered`; it writes Journal
references and clears `name` for `journal`, while non-Journal rows read the
free-text name. Because the spread happens first, extra fields such as
`sceneId` and `maphub` survive a save even when the selected type changes.
[`scripts/hex/HexTooltipSD.mjs:1802-1823`](../../scripts/hex/HexTooltipSD.mjs#L1802-L1823)

### Special readers

- `featureLabel` treats `journal` specially: it resolves the Journal, then an
  optional Page, and falls back to the stored name or `Journal`; all other
  types display the stored name or a capitalized type string. [`scripts/hex/HexTooltipSD.mjs:153-161`](../../scripts/hex/HexTooltipSD.mjs#L153-L161)
- The hover card renders every visible feature as a plain pill. It does not
  render a type prefix, icon, Journal link, scene shortcut, or feature-specific
  control in the pill itself. [`scripts/hex/HexTooltipSD.mjs:221-230`](../../scripts/hex/HexTooltipSD.mjs#L221-L230)
- Only `journal` features with a non-empty `journalId` enter the Journal context
  menu. Only `scene` features with a non-empty `sceneId` enter the GM-only scene
  shortcut list. [`scripts/hex/HexTooltipSD.mjs:603-611`](../../scripts/hex/HexTooltipSD.mjs#L603-L611)
- Generated wilderness, settlement, and text-dungeon content all append a
  `type: "journal"` feature with Journal/Page ids and `discovered: false`.
  Their generator subtype is registered separately (`wilderness`, `settlement`,
  or `dungeon`), not encoded as the feature's UI type. [`scripts/hex/HexTooltipSD.mjs:906-925`](../../scripts/hex/HexTooltipSD.mjs#L906-L925)
  [`scripts/hex/HexTooltipSD.mjs:1038-1059`](../../scripts/hex/HexTooltipSD.mjs#L1038-L1059)
  [`scripts/hex/HexTooltipSD.mjs:1217-1237`](../../scripts/hex/HexTooltipSD.mjs#L1217-L1237)
- Generate Dungeon Map appends both a discoverable Journal feature and a
  separate GM-only `scene` feature. The second carries `sceneId`, `journalId`,
  a `(Map)` name, and `discovered: false`. [`scripts/hex/HexTooltipSD.mjs:1262-1297`](../../scripts/hex/HexTooltipSD.mjs#L1262-L1297)
- Generated settlement rows may carry `maphub` metadata. The context menu
  launches `MaphubViewerApp` from that object; the Edit Hex UI has no field for
  creating or editing it. [`scripts/hex/HexTooltipSD.mjs:1038-1049`](../../scripts/hex/HexTooltipSD.mjs#L1038-L1049)
  [`scripts/hex/HexTooltipSD.mjs:714-730`](../../scripts/hex/HexTooltipSD.mjs#L714-L730)

## 3. Validation, sanitization, defaults, and malformed data

### Editor path

The editor has no feature-specific submit validator. `#collectData` reads the
selected value, checkbox, and text/select values; there is no allowlist check,
required Journal check, Journal existence check, page/Journal consistency check,
or duplicate-id check before `#save` calls `saveHexRecord`. [`scripts/hex/HexTooltipSD.mjs:1766-1841`](../../scripts/hex/HexTooltipSD.mjs#L1766-L1841)

The initial feature name is passed through `foundry.utils.escapeHTML` while
building the input's HTML attribute, but the saved value is subsequently read
from the DOM and stored by `#collectData` without a second output encoding pass.
The tooltip then interpolates the resolved label directly into HTML. Imported
Hexer values take a separate escaping path described below; the Edit Hex path
itself does not establish an escaped-at-rest feature-name format.
[`scripts/hex/HexTooltipSD.mjs:1713-1716`](../../scripts/hex/HexTooltipSD.mjs#L1713-L1716)
[`scripts/hex/HexTooltipSD.mjs:1814-1822`](../../scripts/hex/HexTooltipSD.mjs#L1814-L1822)
[`scripts/hex/HexTooltipSD.mjs:221-228`](../../scripts/hex/HexTooltipSD.mjs#L221-L228)

The Journal list interpolates Journal names into an HTML string, while Page
options are created with `textContent`. That gives the two linked-document
selectors different escaping mechanisms. [`scripts/hex/HexTooltipSD.mjs:1702-1723`](../../scripts/hex/HexTooltipSD.mjs#L1702-L1723)
[`scripts/hex/HexTooltipSD.mjs:1752-1763`](../../scripts/hex/HexTooltipSD.mjs#L1752-L1763)

Changing a row from Journal to another type, or vice versa, only toggles the
visible controls. The collector preserves the existing object first, so stale
`journalId`, `pageId`, `sceneId`, or `maphub` fields can remain attached to a
newly selected type; only the type-specific readers stop using them.
[`scripts/hex/HexTooltipSD.mjs:1737-1747`](../../scripts/hex/HexTooltipSD.mjs#L1737-L1747)
[`scripts/hex/HexTooltipSD.mjs:1805-1822`](../../scripts/hex/HexTooltipSD.mjs#L1805-L1822)

Unknown stored types are not diagnosed. The row builder creates options only
for `FEATURE_TYPES` and marks `selected` only on exact equality; an unknown
stored value has no matching option. Saving then takes whichever option the
browser select exposes, rather than preserving or rejecting the unknown value.
[`scripts/hex/HexTooltipSD.mjs:1697-1700`](../../scripts/hex/HexTooltipSD.mjs#L1697-L1700)
[`scripts/hex/HexTooltipSD.mjs:1802-1812`](../../scripts/hex/HexTooltipSD.mjs#L1802-L1812)

A malformed non-array `features` value is only protected by `?? []`, not by an
array check, in both the tooltip and editor population paths. A malformed
feature missing `type` is likewise not repaired; the non-Journal label fallback
calls `.charAt` on `f.type`. [`scripts/hex/HexTooltipSD.mjs:153-161`](../../scripts/hex/HexTooltipSD.mjs#L153-L161)
[`scripts/hex/HexTooltipSD.mjs:166-179`](../../scripts/hex/HexTooltipSD.mjs#L166-L179)
[`scripts/hex/HexTooltipSD.mjs:1567-1571`](../../scripts/hex/HexTooltipSD.mjs#L1567-L1571)

### Persistence path

The record store is the `__sdx_hex_data__` Journal's `shadowdark-extras.hexData`
flag, keyed first by Scene id and then by hex key. `saveHexRecord` replaces the
entire record at that key and writes the complete `allData` object; it does not
validate or merge feature entries. If the internal Journal does not exist and
the caller is not a GM, the ensure step returns no Journal and the save returns
without writing. [`scripts/hex/HexTooltipSD.mjs:58-82`](../../scripts/hex/HexTooltipSD.mjs#L58-L82)

The separate `mergeHexRecords` API preserves omitted record fields. The builder's
`upsertHexRecords` validates array/entry shape before calling it, but neither that
validation nor `mergeHexRecords` restricts `type` to the Edit Hex list.
[`scripts/hex/HexTooltipSD.mjs:119-139`](../../scripts/hex/HexTooltipSD.mjs#L119-L139)
[`scripts/hex/HexcrawlBuilderSD.mjs:268-303`](../../scripts/hex/HexcrawlBuilderSD.mjs#L268-L303)
[`scripts/hex/HexcrawlBuilderSD.mjs:755-772`](../../scripts/hex/HexcrawlBuilderSD.mjs#L755-L772)

### Import path

The Hexer adapter uses a separate POI map:

- `village`, `town`, and `city` → `settlement`;
- `ruins` → `ruins`;
- `dungeon-entrance` → `dungeon`;
- `cave` → `cave`;
- `tower` → `landmark`;
- `castle` → `fort`;
- `camp` → `settlement`;
- unknown POI types → `other`.

It sets `discovered` from fog visibility, sets `showToPlayers` when a POI is
visible, and escapes feature names after conversion. [`scripts/hex/hexer-data.mjs:13-18`](../../scripts/hex/hexer-data.mjs#L13-L18)
[`scripts/hex/hexer-data.mjs:241-250`](../../scripts/hex/hexer-data.mjs#L241-L250)

## 4. Rendering, visibility, and discovery

The basic card is shown to a player only when the record's `showToPlayers` is
true; GMs bypass that gate. The marker/highlight overview uses the same
record-level visibility gate. [`scripts/hex/HexTooltipSD.mjs:486-502`](../../scripts/hex/HexTooltipSD.mjs#L486-L502)
[`scripts/hex/HexTooltipSD.mjs:526-545`](../../scripts/hex/HexTooltipSD.mjs#L526-L545)

Within a card, GMs see all features and players see only features whose
`discovered` value is truthy. GMs receive a dim CSS class for undiscovered
features; players do not receive those feature elements at all. [`scripts/hex/HexTooltipSD.mjs:166-180`](../../scripts/hex/HexTooltipSD.mjs#L166-L180)
[`scripts/hex/HexTooltipSD.mjs:221-228`](../../scripts/hex/HexTooltipSD.mjs#L221-L228)

The right-click menu has different semantics: GMs see all Journal links and
GM-only scene shortcuts, while players see discovered Journal links only. A
player menu is suppressed only when there are no eligible Journal links; the
code does not also require `showToPlayers`. Journal clicks by a player are sent
through the module socket so the GM side can arrange the needed Journal/Page
permission before rendering. [`scripts/hex/HexTooltipSD.mjs:603-614`](../../scripts/hex/HexTooltipSD.mjs#L603-L614)
[`scripts/hex/HexTooltipSD.mjs:682-711`](../../scripts/hex/HexTooltipSD.mjs#L682-L711)

A missing Journal document is skipped in the context menu, while a missing
Journal during pill-label resolution falls back to the stored name or
`Journal`. A missing Page falls back to the Journal name. [`scripts/hex/HexTooltipSD.mjs:153-161`](../../scripts/hex/HexTooltipSD.mjs#L153-L161)
[`scripts/hex/HexTooltipSD.mjs:620-640`](../../scripts/hex/HexTooltipSD.mjs#L620-L640)

## 6. Mismatches and ambiguities

### A. `scene` is produced but not editable

Generate Dungeon Map writes a `scene` feature, and the context menu has a
specific `scene` reader. `FEATURE_TYPES` does not include `scene`, and the row
builder has no unknown-type handling. Editing and saving such a row therefore
has a plausible path to changing its type to `dungeon` while retaining stale
scene metadata. [`scripts/hex/HexTooltipSD.mjs:51-54`](../../scripts/hex/HexTooltipSD.mjs#L51-L54)
[`scripts/hex/HexTooltipSD.mjs:608-611`](../../scripts/hex/HexTooltipSD.mjs#L608-L611)
[`scripts/hex/HexTooltipSD.mjs:1287-1294`](../../scripts/hex/HexTooltipSD.mjs#L1287-L1294)
[`scripts/hex/HexTooltipSD.mjs:1697-1700`](../../scripts/hex/HexTooltipSD.mjs#L1697-L1700)

### B. `settlement` does not mean the same thing across producers

The Edit Hex UI offers `settlement`, and Hexer imports also emit `settlement`.
The builder's feature-art rules instead recognize `city`, `city_state`, `town`,
and `village`; the builder test fixture uses `town` and proves that it paints a
Specials town tile, while a non-recognized `keyed_location` remains on the
terrain tile. Thus the same record seam currently contains at least two
feature vocabularies, and the UI's `Settlement` value is not the builder's
settlement-art trigger. [`scripts/hex/HexTooltipSD.mjs:51-54`](../../scripts/hex/HexTooltipSD.mjs#L51-L54)
[`scripts/hex/HexcrawlBuilderSD.mjs:179-186`](../../scripts/hex/HexcrawlBuilderSD.mjs#L179-L186)
[`dev/tests/hexcrawl-builder.test.mjs:573-598`](../../dev/tests/hexcrawl-builder.test.mjs#L573-L598)
[`scripts/hex/hexer-data.mjs:13-17`](../../scripts/hex/hexer-data.mjs#L13-L17)

### C. The UI taxonomy is descriptive, not a dispatch table

Except for `journal` and the internal `scene` path, the feature type is only
used to choose a fallback display label in the tooltip. Selecting `dungeon`,
`temple`, `settlement`, or another generic value does not call a generator,
create a document, choose an icon, or change rendering. The generator actions
live in the right-click menu and append linked Journal features independently
of the Edit Hex type list. [`scripts/hex/HexTooltipSD.mjs:153-161`](../../scripts/hex/HexTooltipSD.mjs#L153-L161)
[`scripts/hex/HexTooltipSD.mjs:654-668`](../../scripts/hex/HexTooltipSD.mjs#L654-L668)
[`scripts/hex/HexTooltipSD.mjs:906-925`](../../scripts/hex/HexTooltipSD.mjs#L906-L925)

### D. Visibility has three independent dimensions in the docs, but the context menu bypasses one

The project documentation describes `Show to Players`, per-note visibility,
and per-feature discovery as separate decisions. It also says players receive
discovered Journal links in the right-click menu. The implementation matches
that wording for the menu but does not make the menu depend on `Show to Players`,
so “hidden card” and “no discoverable Journal link” are not equivalent states.
[`docs/wiki/Hexplorer.md:235-249`](../../docs/wiki/Hexplorer.md#L235-L249)
[`scripts/hex/HexTooltipSD.mjs:526-545`](../../scripts/hex/HexTooltipSD.mjs#L526-L545)
[`scripts/hex/HexTooltipSD.mjs:603-614`](../../scripts/hex/HexTooltipSD.mjs#L603-L614)

### E. Linked-document metadata is wider than the editor contract

Generated features can carry `sceneId` and `maphub`, but the editor only exposes
Journal/Page fields when `type === "journal"`, and it exposes no scene or
Maphub controls. The current UI is therefore a partial editor for the persisted
feature objects, not a complete round-trip editor for every producer's shape.
[`scripts/hex/HexTooltipSD.mjs:1038-1049`](../../scripts/hex/HexTooltipSD.mjs#L1038-L1049)
[`scripts/hex/HexTooltipSD.mjs:1287-1294`](../../scripts/hex/HexTooltipSD.mjs#L1287-L1294)
[`scripts/hex/HexTooltipSD.mjs:1737-1747`](../../scripts/hex/HexTooltipSD.mjs#L1737-L1747)

## 8. First-party and domain prior art

### Project-owned evidence

The project's Hexplorer documentation describes the feature list as keyed
locations: Dungeon, Settlement, Landmark, Ruins, Temple, Fort, Cave, Road,
Hazard, Resource, and Other; Journal is described as the linked-document path.
It also documents the per-feature eye as the `discovered` switch and the player
right-click Journal behavior. [`docs/wiki/Hexplorer.md:102-116`](../../docs/wiki/Hexplorer.md#L102-L116)

The same documentation distinguishes generator actions from Edit Hex fields:
Wilderness, Settlement, Dungeon, and Dungeon Map are right-click actions, and
Dungeon Map returns both a Journal link and a GM-only Scene shortcut. [`docs/wiki/Hexplorer.md:174-186`](../../docs/wiki/Hexplorer.md#L174-L186)

The project's provenance note says SDX Hexplorer generator data is an adapted
historical Hexroll 3 corpus, that current Hexroll 3 has materially diverged,
and that SDX consumes its own JSON rather than upstream `.scroll` files.
[`docs/architecture/hexplorer-data-provenance.md:7-29`](../../docs/architecture/hexplorer-data-provenance.md#L7-L29)

### Hexroll/domain evidence

Hexroll's map-editing guide treats dungeon, settlement, river, and realm as
separate map-level operations, and warns that editing generated content acts on
sandbox entities before the visual map is refreshed.[1] Its map guide describes
separate dungeon maps and settlement maps, with settlements covering cities,
towns, and villages.[2] Those concepts explain why SDX has broad location labels
and separate linked-document/map behavior, but they do not define SDX's current
12-value enum.

The current Hexroll 3 project is the work-in-progress generator/VTT repository
behind `hexroll.app`.[5] Its `Hex` model is more open-ended than the SDX row
list: it can contain optional `Residency`, `Dungeon`, `Settlement`, `Inn`,
`Encounter`, `Feature`, and `QuestObject` entities.[6] Its modding guide defines `Feature` as
an extensible class family and gives examples such as WaterWell, Bridge,
Watchtower, DeadAdventurers, AbandonedVillage, Altar, and SignalingTower rather
than a closed UI enum.[3][7] This is domain prior art for treating many SDX
values as descriptive categories, not evidence that the SDX strings are an
upstream schema.

Hexroll 3's settlement corpus explicitly uses Village, Town, and City classes,
while its dungeon corpus defines Temple, Tomb, and Cavern classes.[8][9][10] That
vocabulary aligns with parts of the SDX list but also exposes the current
boundary: SDX's UI has `settlement`, `temple`, and `cave`, while its builder and
Hexer adapter use other strings (`city`/`town`/`village` and `settlement`).

The Hexroll landing page describes interactive hex, dungeon, and settlement
maps, editing/re-rolling sandbox entities, and map/VTT reveal hex by hex.[4]
This supports the broad SDX concepts of generated linked content and discovery,
not the exact implementation or storage shape.

### Name collision: external Foundry Hexplorer

The Foundry package listing for **Hexplorer** identifies a separate add-on module
by TheRipper93, described as a toolkit for hex fog, colored zones, time
advancement, and table rolling.[11] The SDX project has its own Hexplorer wiki
and implementation; this audit found no evidence that the external Foundry
package supplies the SDX feature enum. Treat the shared name as a disambiguation
issue, not as implementation lineage. The project's own wiki is the relevant
first-party documentation for this module.[12]

## Bottom line

The current UI is a compact keyed-location taxonomy layered over a looser
`features[]` record seam. Its stable behavioral contract is not the visible
list itself: it is the special handling of `journal`, the internal generated
`scene` shortcut, the `discovered` flag, and the record-level `showToPlayers`
gate. The highest-confidence mismatches are the non-editable `scene` type, the
`settlement`/`town` vocabulary split between UI/importer and builder rendering,
and the absence of direct Edit Hex feature-row tests. All findings above are
static unless explicitly marked by the test command result.
